Q/01 Before we start

Questions from last time?

Anything from L01–L03 that still feels unclear. If the room is quiet, we answer these three.

01

What does a browser actually do with a file we send it?

It parses the HTML into a tree of objects (the DOM), applies styles, and renders pixels on screen.

02

What is the difference between HTML, CSS, and JavaScript?

HTML is structure (what is on the page), CSS is style (how it looks), JavaScript is behavior (what it does).

03

Why do we need to declare a language with lang="en"?

Screen readers use it to choose the right voice. Search engines use it for regional results. Spell-checkers use it too.

5 minutes. Let students ask first. Only then press next to show backup questions one by one; click the cover to reveal each answer.

S/01 First look

The smallest valid HTML document

Every HTML page needs exactly these four things. Everything else is content.

Line 1

<!DOCTYPE html>

Not a tag — a declaration. Tells the browser: "parse this as modern HTML5, not quirks mode."

Lines 2–10

<html lang="en">

The root element. lang is the document's language — used by screen readers and search engines.

Lines 3–7 · Inside <html>

<head> and <body>

Two direct children, always. head is metadata — nothing visible. body is everything the user sees.

Type this live. Use VS Code's ! emmet shortcut to generate it, then explain each line. Students should be surprised at how little is needed for a valid page.

S/02 The declaration

<!DOCTYPE html>

It is not a tag. It is a declaration to the browser's rendering engine.

What happens without DOCTYPE?

Without DOCTYPE, most browsers enter quirks mode — a backwards-compatibility mode that mimics browser bugs from the 1990s. Layouts break in unpredictable ways. Always put DOCTYPE on line 1.

Hands up first, then click. The "quirks mode" answer surprises students. It's a real problem: old tutorials online sometimes omit DOCTYPE and the pages look fine in Chrome — until a different browser loads them.

S/03 The head element

The head: metadata, not content

Nothing in <head> is visible in the page — but every item matters.

<meta charset="utf-8">

Character encoding

Tells the browser which characters are in the file. Without it, Georgian text (and emoji) show as gibberish.

<meta name="viewport" …>

Viewport

Tells mobile browsers to render at the device width rather than zooming out to a desktop view. Needed for any responsive layout.

<title>

Page title

Shows in the browser tab, bookmark, and search results. Write it as if it is the only thing a user sees about your page.

<link rel="stylesheet" href="…">

Stylesheet link

Connects an external CSS file. We will add this in the CSS lecture. It has no visible content — it is a void element.

<link rel="icon" href="…">

Favicon

The small icon in the browser tab. A 32×32 PNG works; .ico also works. Not required, but memorable.

<meta name="description" …>

Description

A short summary that appears under the page title in Google search results. Keep it under 160 characters.

Go through each card. Ask the class what each one does before revealing. The charset one: "try removing this and type in Georgian — watch what happens."

S/04 The viewport meta

Why width=device-width matters

Without this meta tag

Mobile browsers assume the page was designed for a 980 px desktop. They zoom out to fit it, making text tiny. The user must pinch-zoom to read anything. Your carefully structured page looks broken.

With this meta tag

The browser renders at the actual device width. A phone renders at 390 px, a tablet at 768 px. CSS media queries then let you adapt the layout per screen size — which we cover in a later lecture.

S/04 What each part does

PartMeaning
width=device-widthViewport = the physical screen width
initial-scale=1Start at 1× zoom, no shrinking

Always put this meta tag in the head. Never set user-scalable=no — it breaks accessibility by preventing pinch-zoom for visually impaired users.

Open DevTools device mode. Toggle it off and on while looking at a page without the viewport meta to show the difference. Students are often surprised this one tag makes such a visible change.

S/05 The full picture

Every HTML document has this shape

<html>
<head> — metadata
<meta charset="utf-8">
<meta name="viewport" …>
<title>Le Bistro</title>
<link rel="stylesheet" href="style.css">
<body> — visible content
<h1>Menu</h1>
<p>Today's specials…</p>
<ul><li>Coq au vin</li>…</ul>
<a href="…">Reserve</a>
<button>Order now</button>

The tree has two parts: metadata the browser uses, and content the user sees.

The rule

Head = for the browser.
Body = for the user.

If you are not sure where something goes: if it is visible, it goes in the body. If it is invisible metadata or a resource link, it goes in the head.

Opening DevTools in any browser and looking at the Elements panel shows you this exact tree for any page on the web. Try it now.

Point at the diagram. "Everything in orange is the head — metadata. Everything in green is the body — what the user sees." Ask: where does a <script> tag go? (Usually end of body, or head with defer.) Where does a <link> to a font go? (Head.)

S/06 Quick check

Head or body?

For each item, say whether it belongs in <head> or <body>. Hands up, then we check.

Item A

<title>Le Bistro</title>

Head. The title is not visible on the page — it shows only in the browser tab and search results.

Item B

<h1>Today's Menu</h1>

Body. Headings are visible content. Anything the user reads or sees goes in the body.

Item C

<link rel="stylesheet" href="style.css">

Head. It is a resource link — no visible output, but the browser needs it to style the page.

Item D

<img src="logo.png" alt="Logo">

Body. An image is visible content. It goes in the body, usually inside a meaningful element.

Item E

<meta name="description" content="…">

Head. It is metadata — not visible, used by search engines and social media link previews.

Item F

<p>Open Tuesday–Sunday.</p>

Body. A paragraph is visible content for the user. Always in the body.

Reveal each card one by one. Students often hesitate on the stylesheet link. Reinforce the rule: "If the user sees it, body. If the browser uses it but the user does not see it, head."

E/01 What goes in the body

The elements you use every day

These twelve cover ninety percent of real pages. Learn them well and the others follow easily.

heading<h1>–<h6>

Six levels of heading. Convey hierarchy — not visual size. Use only one h1 per page.

paragraph<p>

A block of text. The browser adds spacing above and below. Default for prose.

list<ul> / <ol>

Unordered (bullets) or ordered (numbers). Items go inside <li>.

inline<strong> / <em>

<strong> = important, renders bold. <em> = stress emphasis, renders italic.

link<a>

Navigates to a URL or another page. Requires href. Use for navigation.

image<img>

Embeds an image. Requires src and alt. A void element — no closing tag.

button<button>

Triggers an action. Use for forms and interactivity — not for navigation.

line break<br>

A single line break. A void element. Use sparingly — prefer margins in CSS.

horizontal rule<hr>

A thematic break. Marks a change of topic. Renders as a line, but has semantic meaning.

definition list<dl>

Term-description pairs. Great for glossaries, menus with descriptions, key-value data.

container<div>

A generic block container with no meaning. Use only when no semantic element fits.

inline container<span>

A generic inline container with no meaning. Use for styling a run of text.

Go through each card. For each one, ask the class to give a real example from any website they know. Emphasize: "we use these every single day."

E/02 Heading elements

Six levels — but only one is the title

h1Le Bistro
h2Today's Specials
h3Main Courses
h4Coq au Vin
h5Description
h6Allergens

Do not pick headings for their visual size

Use CSS to control how big a heading looks. The heading level communicates hierarchy to search engines and screen readers — a screen reader user navigates pages by jumping between headings. A wrong level breaks that navigation.

Rule: one <h1> per page — it is the page's title. Never skip levels (no h1 → h3 with no h2 in between).

Show the visual scale on the left. Then open any news site: "find the h1." They will see the article title. Ask: "why is the site name usually NOT in an h1?" (It would be a new h1 on every page — the article title is the page's topic.)

E/03 Hierarchy matters

The heading outline of a real page

Good outline

h1: Le Bistro
h2: Menu
h3: Starters
h3: Mains
h4: Coq au vin
h2: Reserve

Broken outline

h1: Le Bistro
h3: Menu ←
h5: Starters ←
h2: Reserve

A heading outline is like a table of contents. Screen readers read it aloud for navigation.

  • Use h1 once — it names the page.
  • Always nest in order: h2 follows h1, h3 follows h2.
  • Never skip levels to get a visual effect — use CSS instead.
  • Don't use headings just to make text big. Use a span and CSS.

Screen reader users use the H key to jump between headings on a page. A broken outline means they cannot navigate. This affects about 2–3% of users.

Show the contrast between good and broken outlines. "The broken outline is not wrong to the eye — the page looks the same. But the screen reader cannot navigate it." Open a real site in an accessibility tool to show the heading outline if time allows.

E/04 List elements

Three kinds of list

Unordered

<ul>

Items have no fixed order. Renders as bullet points by default. Use for navigation menus, ingredient lists, tag lists.

Ordered

<ol>

Items have a meaningful sequence. Renders as numbered list. Use for steps, rankings, cooking instructions.

Description list

<dl>

Term-description pairs. Use for menus with descriptions, glossaries, metadata key-value pairs.

Never put anything except <li> as a direct child of <ul> or <ol>. The HTML spec requires it, and browsers may fix it in ways you did not expect.

Ask: "on our restaurant menu page — which list type for the menu items? Which for the preparation steps?" A menu is usually ul (order doesn't matter for items). Steps are always ol. A menu with prices is a perfect dl.

E/05 The anchor element

Links connect pages — and ideas

href "menu.html"

Where to go

Relative = same site. Absolute (https://…) = external site. #id = same-page scroll.

target "_blank"

Open in new tab

Only use for external links. Never for same-site navigation — users find new tabs disorienting.

rel "noopener"

Security

Required with target="_blank". Prevents the new page from accessing your page via window.opener.

Type these live. Show what happens if you omit the href — the link still renders but goes nowhere and loses its tab-stop. Mention: relative vs absolute paths. "When do you use absolute?" (Always for external sites. Only for same-site when you have a known base URL.)

E/06 Embedding images

Images: src, alt, and nothing else

Missing alt — never acceptable

Screen readers say "image" with no description. Search engines cannot index the image. If the image fails to load, the user sees nothing. Always write meaningful alt text.

AttributePurposeRequired?
srcImage URL or pathYes
altText descriptionYes (empty ok for decorative)
width/heightReserve layout spaceStrongly recommended
loading="lazy"Defer off-screen imagesRecommended

Show an img without alt — the browser console logs a warning. "Decorative images still need alt=''. The empty string tells screen readers to skip this image." The width/height attributes prevent layout shifts as the page loads (CLS metric).

Boolean attributes

No value needed

Some attributes are true just by being present: disabled, checked, required, hidden. No ="true" needed.

Custom data attributes

B/01 The most common mistake

Button vs. link — not the same thing

<button>

Triggers an action

When to use
  • Submit a form
  • Open/close a modal
  • Add item to cart
  • Toggle something on or off
  • Any JavaScript action on this page
<a>

Navigates somewhere

When to use
  • Go to another page
  • Jump to a section on this page
  • Open an external website
  • Download a file (download attr)
  • Anything that changes the URL

If clicking it would change the URL — use <a>. If it does something on the current page — use <button>.

This is the most common mistake developers make. Ask the class: "you've seen buttons styled as links and links styled as buttons — why does it matter?" Answers: screen readers announce "link" vs "button", keyboard users expect different behavior, mobile browsers handle them differently.

B/02 Always set the type

Three button types — default is dangerous

type="button"

Does nothing by default

Triggers only JavaScript you attach. Use for all non-form buttons: modals, toggles, actions.

type="submit"

Submits the form

Submits the nearest ancestor <form>. This is the default when no type is set — which is the dangerous part.

type="reset"

Clears the form

Resets all form fields to their default values. Rarely used — most users find accidental resets very frustrating. Use with caution.

Always set type explicitly

A <button> inside a <form> without a type defaults to submit. If you meant it to be a toggle or modal trigger, it will accidentally submit the form. This is a very common bug.

Show the bug live: add a button with no type inside a form, click it — the form submits. Now add type="button" — it no longer submits. Students often encounter this exact bug before they know why it happens.

B/03 Quick check

Button or link for each of these?

Scenario A

"Add to cart" on a menu item

Button. It does something on the current page — updates state. The URL does not change. Use <button type="button">.

Scenario B

"View full menu" on the homepage

Link. It navigates to a different page. Use <a href="menu.html">.

Scenario C

"Close" on a modal overlay

Button. It dismisses the modal — an action on the current page, no navigation. Use <button type="button">.

Scenario D

"Download our PDF menu"

Link. It navigates to a file. Use <a href="menu.pdf" download>. The download attribute triggers a download instead of opening the file.

Cover each scenario before revealing. Scenario B is the one students most often get wrong — they think a visually styled button means a button element. Emphasize: appearance ≠ semantics.

Sum/01 You explain it

Cover the card. What's on the other side?

Click the card to check. If you are wrong, re-read the slide before the next lecture.

01

What does <!DOCTYPE html> do?

Reveal

Tells the browser to use modern HTML5 rendering mode, not quirks mode. Always goes on line 1, before anything else.

02

What is the difference between <head> and <body>?

Reveal

<head> holds metadata the browser uses but the user does not see. <body> holds all visible content.

03

Why does the viewport meta tag exist?

Reveal

Without it, mobile browsers zoom out to a desktop width. It tells them to render at the device's physical width so CSS can adapt the layout.

04

Why must every <img> have an alt attribute?

Reveal

Screen readers read alt text aloud. Search engines use it. If the image fails to load, alt text shows. Decorative images use alt="" to tell screen readers to skip them.

05

When do you use <a> vs. <button>?

Reveal

Use <a> to navigate (change URL). Use <button> to trigger an action on the current page. Never style a link to look like a button and call it a button.

06

What happens if you skip heading levels?

Reveal

Screen readers announce the heading level. Jumping from h1 to h3 breaks the outline and confuses users who navigate by headings. Use levels in order; use CSS for visual size.
